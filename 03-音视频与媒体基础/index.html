    03 音视频与媒体基础¶

    状态：🟡 已填充 3.0 / 3.1 / 3.2 / 3.3 / 3.4 / 3.6，待补真实 SDP 样例与 3.5.8 ｜ 难度：★★☆☆☆ 3.4 已含：RTP 头 → RTCP(SR/RR) → 抗丢包 → 与 RTSP/RTMP/HLS 对比 → 3.4.6 音视频分路打包 / 3.4.7 接收端与 NetEq / 3.4.8 音画同步。 本章要解决的问题：画面到底是怎么从"摄像头"变成"另一台手机屏幕上的一帧"的？

    为什么需要这一章¶

    前面 01 章已经知道媒体是 P2P 的 RTP 包。但"打包"之前，音视频原始数据经历了 采集 → 编码 → 封包；接收端反向 拆包 → 解码 → 渲染。这一章把中间的每一步讲透，理解后才能回答诸如： - 为什么分辨率/帧率约束写在 getUserMedia 的 mandatory 里？ - 为什么 SDP 里会列出 H.264/VP8 一堆编码？两端到底选了哪个，怎么得知？ - RTMP / RTSP / RTP / H.264 / H.265 到底谁是"视频流"？（3.0 先分层，别串味） - 为什么偶发卡顿/马赛克？（丢包、无 FEC/NACK） - 为什么相机端 CPU 发热？（编码很贵，且很可能是软编 → 3.2.7、07 章 P4） - 为什么回放不是"看直播"而是"下文件"？（3.6）

    内容骨架¶

    3.0 先分层：编码 ≠ 容器 ≠ 传输¶

    状态：🟢 已填充 这一节是整章的"总纲"。搞不清这一节，后面所有概念都会串味。

    学 WebRTC 时最常被这几个词绕晕：RTMP / RTSP / RTP / H.264 / H.265。它们经常被并列放在一起说，但根本不在同一个层级上：

    名称 本质 所处层级 它是不是"视频流"？
    H.264 / AVC 视频压缩编码标准 编码层（Codec） ❌ 它只是"怎么把像素压成字节"的算法
    H.265 / HEVC 视频压缩编码标准（H.264 的下一代） 编码层 ❌ 同上
    VP8 / VP9 / AV1 视频压缩编码标准（Google 系） 编码层 ❌ 同上
    RTP 实时传输协议（配套 RTCP 做质量反馈） 传输层（通常跑 UDP） ✅ 承载层：只管"分包 + 时间戳 + 序号"
    RTSP 实时会话控制协议（文本协议，像 HTTP） 控制/信令层 ❌ 它只发 DESCRIBE/SETUP/PLAY，不传数据
    RTMP Adobe 的一体化流媒体协议（自带封装 + 传输） 封装 + 传输层（TCP） ✅ 完整方案，自成一套

    分层之后是这样叠起来的：

    原始像素
   ↓  〔编码层〕H.264 / H.265 / VP8 / VP9 / AV1  —— 决定"怎么压"
压缩后的帧（裸码流）
   ↓  〔封装层〕Annex-B / AVCC / FU-A            —— 决定"怎么摆"（见 3.2.6）
   ↓  〔传输层〕RTP/SRTP（UDP） 或 RTMP（TCP）   —— 决定"怎么送"
网络包
   ↑  〔控制层〕RTSP / SDP / 自定义信令          —— 只是"遥控器"，不传数据

    一句话记忆

    编码决定"怎么压"，封装决定"怎么摆"，传输决定"怎么送"，控制层只负责"怎么约"。 四者正交、可自由组合：RTMP 里可以装 H.264；RTP 里也可以装 H.264；RTSP 控制的那条 RTP 里同样可以是 H.264 或 H.265。 所以"用 RTMP 还是用 H.264"是个伪问题——它们不在同一个选项集里。

    本项目一个字都没用到 RTSP / RTMP / HLS

    本项目（相机端 ↔ 监控端，两端都是自己的 App）全程只走 WebRTC：信令用 WSS、媒体用 SRTP、回放用 DataChannel 传文件。 本章之所以仍要讲 RTSP/RTMP，是因为排查问题时最容易把这几套方案张冠李戴——见 3.4.4 的横向对比。

    3.1 数字音视频的基本概念¶

    状态：🟡 要点已填充

    概念 视频 音频
    最小单位 帧（一张图） 采样点
    每秒多少个 帧率 fps（25/30/60） 采样率 Hz（48000 / 16000）
    单位大小 分辨率（1920×1080） 位深（16 bit）+ 声道（1/2）
    原始排列 像素格式：I420 / NV12 / BGRA（见 09 章 9.4） PCM
    每秒数据量 分辨率 × 帧率 × 1.5 字节 采样率 × 位深/8 × 声道

    码率（bitrate）= 数据量 / 时间，是"画质 ↔ 带宽"的权衡旋钮。一段 1080p30 的未压缩 YUV：

    1920 × 1080 × 1.5 字节 × 30 帧 ≈ 93 MB/s ≈ 750 Mbps

    而压缩后（H.264）通常只要 2~5 Mbps——差了两个数量级，这就是编码存在的意义。

    本项目的采集约束对应关系：signaling.dart:607-626 的 mediaConstraints 里写 minWidth/minHeight/minFrameRate，这是对采集的期望（注意是"期望"不是"承诺"，实际会被设备能力与带宽自适应改写——详见 09 章 9.7）。 它约束的是分辨率/帧率，与用什么编码无关。

    3.2 编解码器（Codec）¶

    状态：🟢 已填充

    3.2.1 为什么必须压缩（1 秒 1080p 未压缩 ≈ 上百 MB）¶

    见 3.1 的算式。不压缩就没法在网络上实时传，这是硬约束。

    3.2.2 H.264 / AVC 与 H.265 / HEVC¶

    命名要先说清：一个标准、两个名字——视频编码标准由 ITU-T 和 ISO/IEC 联合发布，所以同一份标准有两套编号：

    通俗叫法 ITU-T 编号 ISO/IEC 编号 正式英文名（缩写）
    H.264 H.264 MPEG-4 Part 10 AVC = Advanced Video Coding
    H.265 H.265 MPEG-H Part 2 HEVC = High Efficiency Video Coding

    所以 H.264 == AVC，H.265 == HEVC，就是"土豆"和"马铃薯"。代码里见到 video/avc、avc1、hvc1，指的就是它们。

    维度 H.264 / AVC（2003） H.265 / HEVC（2013）
    压缩率 基准 同画质省约 40~50% 码率
    基本单元 宏块固定 16×16 CTU 最大 64×64，四叉树自适应切分
    帧内预测方向 9 种 35 种
    编码复杂度 基线 编码端 2~10 倍，解码端 1.5~2 倍
    专利授权 MPEG LA 一家，清晰 三家专利池（MPEG LA / HEVC Advance / Velos），混乱
    生态支持 几乎所有芯片/浏览器全部支持 硬件与浏览器支持残缺
    WebRTC ✅ 支持 ❌ 不支持（libwebrtc 无 HEVC）

    H.265 没进实时通信领域的根因

    H.265 是"用 2~10 倍编码算力 + 一堆专利麻烦，换 40% 带宽"。 移动端长时间推流时，编码算力直接转换成发热和耗电——本项目相机端正是"一部手机开着摄像头连续推流数小时"，这笔账是亏的。

    3.2.3 VP8 / VP9 / AV1（Google 系，免专利）¶

    这是另一条 lineage，和 ITU/ISO 的 H.26x 系列是竞争关系：

    编码 出身 对标 关键卖点
    VP8 On2 开发，Google 2010 收购后开源 H.264 免版税（royalty-free）
    VP9 Google 自研 H.265 效率接近 HEVC，但编码复杂度远低于 HEVC
    AV1 AOMedia 联盟（Google/Netflix/Amazon/Apple…） 超越 H.265 免专利 + 比 VP9 再省 30%，但算力极高
    • VP8/VP9 通常装在 WebM 容器里，配 Opus/Vorbis 音频——这是 Google 的一整套免专利组合拳。
    • VP8 是 WebRTC 的强制项：RFC 7742 规定 WebRTC 实现必须支持 VP8 和 H.264（音频必须支持 Opus 和 G.711）。这就是"任何两个 WebRTC 端点一定能通话"的兜底。
    • VP8/VP9 没有 NALU 概念（见 3.2.5），它们是"帧 + 自带 frame header"的结构，参数写在帧头里，不需要额外传参数集。

    3.2.4 压缩到底怎么做的：四类冗余¶

    编码器干的事，就是找出并扔掉四类冗余：

    冗余类型 大白话 做法
    时间冗余（贡献最大） 相邻两帧几乎一样，只有一小块在动 运动估计/运动补偿：在上一帧"找"这块内容跑哪去了，只记运动矢量（"这块往右挪 30px"）+ 一小块残差
    空间冗余 一整片蓝天，不用逐像素记 帧内预测：用周围已编好的像素"猜"当前块，只编码猜不准的差值
    视觉冗余（有损的根源） 人眼对亮度敏感、对颜色不敏感；对轮廓敏感、对细微纹理不敏感 ① 4:2:0 色度抽样（颜色信息砍到 1/4）
    ② DCT 变换 + 量化：转频域后把高频系数按 QP 成批抹零
    编码冗余（无损） 数据里还有统计规律（比如一串 0） 熵编码（CAVLC / CABAC），类似 ZIP

    量化步长 QP 就是平时说的"画质/码率旋钮"：QP 越大 → 抹掉越多 → 码率越低、画面越糊（块效应、振铃）。

    三种帧类型（由时间冗余引出）：

    帧 参考谁 特点
    I 帧（关键帧 / IDR） 自包含，不参考别人 体积最大；是随机访问点（拖动进度条）和错误恢复点
    P 帧 只参考前面的帧 靠运动矢量 + 残差
    B 帧 前后双向参考 压缩率最高，但要等"未来帧"到达 → 引入缓冲延迟

    为什么实时通话基本不用 B 帧

    B 帧要求"后面的帧先到"，天然带来乱序和缓冲。追求亚秒级延迟的 WebRTC/直播场景通常禁用 B 帧——这也是"实时流"和"离线压制"画质/延迟取舍的分水岭。 本项目没有干预这项，由 libwebrtc 按实时场景默认处理。

    一串从一个 I 帧到下一个 I 帧之间的帧叫一个 GOP（Group of Pictures）。本项目录 10 秒一段 MP4，GOP 长度直接影响起播与拖动体验。

    3.2.5 编码器的产物：裸码流与 NALU¶

    裸码流（Elementary Stream, ES） = 只有编码压缩后的视频数据本身，没有外面那层包装：

    层级 例子 能否直接播放
    裸码流 ES .h264 / .hevc 文件 ❌ 能解码，但没有时间戳、没有音轨、没有元数据，没法"播放"
    + 时间戳 = PES TS 流里的一路 部分
    + 容器封装 .mp4 / .mov / .ts ✅ 完整可播放

    H.264 把裸码流组织成一串 NALU（Network Abstraction Layer Unit），每个 NALU 有类型：

    NALU 类型 内容 属于
    SPS 全局参数：分辨率、profile、level non-VCL
    PPS 图像参数：熵编码方式、QP 等 non-VCL
    IDR / I 帧片 关键帧数据 VCL（真像素）
    非 IDR 片 P/B 帧数据 VCL
    SEI / AUD 附加信息 / 分隔符 non-VCL

    SPS/PPS 必须先给到解码器

    否则解码器就算拿到帧数据也不知道怎么解（不知道分辨率和参数）。"SPS/PPS 放哪儿"正是下面三种摆放方式的核心差异。

    3.2.6 裸码流的三种摆放方式：Annex-B / AVCC / RTP¶

    NALU 长度任意（SPS 可能 30 字节，1080p 的 I 帧可能 500 KB）。三种格式本质上都在解决"这一串 NALU 怎么被正确读出来"，但约束条件不同：

    Annex-B AVCC RTP（RFC 6184）
    本质 字节流的定界格式 文件的定界格式 网络传输协议
    解决什么问题 连续字节流里找边界 文件中精确定位 MTU 适配 + 时序 + 丢包/乱序
    分隔方式 起始码 00 00 00 01 长度前缀（通常 4 字节） 不需要（UDP 包天然有边界）
    SPS/PPS 内联在流里，关键帧前重复发 抽到 avcC box（带外） SDP 的 sprop-parameter-sets 或 STAP-A
    大 NALU 怎么办 不管（整块写） 不管（整块写） FU-A 主动分片
    时间戳/丢包检测 ❌ ❌ ✅
    随机访问 差（要扫字节） 好（可算偏移） 不适用
    中途接入 好（随时拿到参数） 差（必须先读头） 好
    典型场景 TS、直播、.h264 MP4 / MOV / MKV WebRTC、RTSP+UDP 
    Annex-B : ... 00 00 00 01 [SPS] 00 00 00 01 [PPS] 00 00 00 01 [I帧 500KB] ...
AVCC    : [00 00 00 1E][SPS 30B]  [00 00 07 A1 20][I帧 500KB] ...
                长度=30                长度=500000
RTP     : 500KB 的 I 帧 → 拆成几百个 FU-A 包，每包带「开始/中间/结束」标志

    Annex-B ↔ AVCC 可以无损互转

    只是换分隔符、搬 SPS/PPS 位置，NALU 内容一个字节都不变。FFmpeg 的 h264_mp4toannexb / h264_annexbtoavcc 就是干这个的。

    最精妙的对比点

    起始码/长度前缀的存在，是因为"没有天然边界"；而 UDP 包本身就是天然边界。 所以 RTP 不需要任何一种定界符，它需要的反而是相反的能力——把一个太大的 NALU 拆开（FU-A）。 RFC 6184 定义了：Single NALU（小包直通）、FU-A（大 NALU 分片，最常用）、STAP-A（多个小 NALU 聚合，常用来一起发 SPS+PPS）。

    本项目链路对照：编码器输出 → libwebrtc 内部 → RTP（FU-A/STAP-A） 发给监控端；同时本地录制分支另走 MP4（AVCC） 落盘——详见 3.6。

    3.3 SDP：编码能力是"怎么约定"的¶

    状态：🟢 已填充（真实 SDP 样例仍是 TODO） 这一节回答一个关键问题：发送方和接收方是怎么知道对方用什么编码、用什么摆放方式的？

    3.3.1 SDP 长什么样¶

    SDP（Session Description Protocol，RFC 4566）就是一段纯文本的"自我介绍书"，不是传输协议。行格式固定为 x=value：

    行 含义
    v= / o= / s= / t= 版本 / 会话发起者 / 会话名 / 时间
    c= 连接信息
    m= 媒体行：m=<媒体类型> <端口> <传输协议> <payload type 列表>
    a=rtpmap payload type ↔ 编码格式 的映射声明
    a=fmtp 该编码的附加参数
    a=sendrecv / sendonly / recvonly 媒体方向
    a=mid Unified-Plan 下一条 m-line 的标识
    a=ice-ufrag / a=fingerprint … ICE 与 DTLS 参数（见 04 章）

    Unified-Plan：一条 m-line = 一个 transceiver（收发器）。本项目 sdpSemantics: 'unified-plan'（signaling.dart:115），现代标准，旧的 plan-b 已废弃。

    本项目方向：相机端发画面（sendonly），监控端收画面；监控端开启对讲时会重协商加入麦克风轨（见 setMonitorTalkbackEnabled()，signaling.dart:253-295）。 ⚠️ 注意 offer 里 OfferToReceiveAudio/Video: true 声明的是"我想收"，不是"我能发"。

    3.3.2 核心机制：payload type 映射表¶

    这是"怎么约定"的真正答案。RTP 包头里只有 7 bit 的 Payload Type 字段（0~127），双方要做的就是约定好"几号 = 什么编码"这张表：

    • 0~95 静态编号（IANA 固定分配，如 0 = PCMU 音频）——视频基本没分到静态号
    • 96~127 动态编号——必须由 SDP 临时声明含义

    一段真实的 video m-line：

    m=video 9 UDP/TLS/RTP/SAVPF 96 97 98 99 100 101 102
                             ↑ 顺序 = 优先级，越靠前越想要
a=rtpmap:96 VP8/90000
a=rtpmap:97 rtx/90000
a=rtpmap:98 H264/90000
a=fmtp:98 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f
a=rtpmap:100 VP9/90000
a=rtpmap:102 red/90000
    行 含义
    96 97 98 … 本端支持的所有 payload type，按偏好排序
    a=rtpmap:96 VP8/90000 96 号 = VP8，时钟 90000 Hz（视频固定 90 kHz）
    a=rtpmap:98 H264/90000 98 号 = H.264
    rtx / red / ulpfec 重传 / 冗余 / 前向纠错的辅助"编码"（可靠性产物，不是原始数据）

    协商只做一次（握手时传 SDP），此后每个 RTP 包只用 7 bit 说自己是几号，接收方查表交给对应解码器——这就是为什么实时传输不需要每包带冗长的格式描述。

    3.3.3 offer/answer 协商规则（RFC 3264；WebRTC 走 JSEP RFC 8829）¶

    ① 发起方 offer  : 列出自己支持的所有 codec，按偏好排序
② 应答方 answer : 只能从 offer 的列表里挑自己支持的
                  ✗ 不能引入 offer 里没有的 codec
                  ✓ 可以裁剪掉自己不支持的
                  ✓ 可以重排顺序，表达自己的偏好
③ 最终生效      : 取 answer 里排在最前面的那个

    真正的双向对话，且 answer 可以"降级"——这正是跨设备兼容性的来源。

    3.3.4 fmtp 里唯一被协商的"打包细节"¶

    Annex-B vs AVCC 从不协商（由容器规范写死，见 3.2.6）。但 RTP 有一个真正需要协商的打包参数：

    a=fmtp:98 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f
    参数 含义
    packetization-mode 0 = 只允许 Single NALU（大帧发不出去，基本不可用）
    1 = 允许 FU-A 分片 + STAP-A 聚合（实际必选）
    profile-level-id H.264 的 profile/level（如 42e01f = Baseline Level 3.1）。两端必须匹配，否则可能协商失败或解码异常
    level-asymmetry-allowed=1 允许收发使用不同 level（如发 720p、收 480p）
    sprop-parameter-sets base64 的 SPS/PPS，带外提前告知（也可改用 STAP-A 带内发送，中途重连更可靠）

    3.3.5 设备怎么知道"我支持什么"？（三层叠加）¶

    这是个高频疑问。答案是三层共同决定，WebRTC 只规定最底下那层：

    层 谁决定 决定什么
    ① 标准下限 RFC 7742（视频）/ RFC 7874（音频） WebRTC 实现必须支持 VP8 + H.264 Constrained Baseline；音频必须支持 Opus + G.711。这是互通性兜底，不禁止支持更多
    ② 编译全集 libwebrtc 的 GN 编译开关（rtc_use_h264 / rtc_libvpx_build_vp9 / rtc_enable_av1）+ 预编译产物版本 编解码器是编进 .so / .framework 的，版本锁死则全集固定
    ③ 运行时子集 查询平台硬件 Android 用 MediaCodecList 按 MIME 枚举（MIMETYPE_VIDEO_AVC/HEVC/VP8/VP9/AV1）；iOS 用 VideoToolbox（H.264 全系硬编，HEVC 需 A10+）。硬件不支持则回落软编或不可用

    推论：同一份 Flutter 代码，在不同手机上生成的 SDP 可能不一样

    第 ③ 层是设备相关的。所以不能靠推理断定"本项目一定在用什么编码"，必须运行时实测。

    ⚠️ H.264 的历史包袱：开源 libwebrtc 默认不自带 H.264（专利 + 需链接 OpenH264/FFmpeg），必须显式开 rtc_use_h264=true。 本项目用的是 flutter-webrtc 维护的预编译产物（Android io.github.webrtc-sdk:android:150.7871.01，android/app/build.gradle:122；iOS 同版本 CocoaPods），一般已启用——但这点必须实测确认，不能想当然。

    3.4 RTP / RTCP：媒体怎么在网络上跑¶

    状态：🟢 已填充

    3.4.1 RTP 头：7 bit 说清"我是什么编码"¶

    RTP（RFC 3550）跑在 UDP 上，每个包只负责搬运，不管重传、不管顺序：

    ┌─ RTP 头 ────────────────────────────────┬─ RTP 载荷 ─────────┐
│ PT=98 │ seq │ timestamp │ SSRC │ marker │  编码后的 NALU 数据 │
└─────────────────────────────────────────┴────────────────────┘
    字段 作用
    Payload Type（7 bit） 编码格式代号 → 查 SDP 建的表
    Sequence Number 重排序（UDP 会乱序）+ 检测丢包
    Timestamp 采样时刻 → 接收端用 jitter buffer 按正确节奏播放，消除网络抖动
    SSRC 同步源标识 → 区分多路流
    Marker bit 视频里常用来标"这是一帧的最后一个包"

    同一帧的多个 FU-A 包共用同一个 timestamp（90 kHz），接收端据此拼回一帧。

    3.4.2 RTCP：质量反馈（RTP 的孪生兄弟，必须配套）¶

    RTCP 周期性互发收发报告：丢了多少包、抖动多大、往返时延多少。发送端据此做拥塞控制与码率自适应——网络差了就降码率。

    这就是 WebRTC 能做到"不卡"的核心机制。本项目完全交给 libwebrtc，代码不感知。

    RTCP 不止"汇报丢包"，两类报文分工不同：

    报文 谁发 内容 用途
    SR（Sender Report） 发送端 发包数/字节数 + NTP 时间戳与对应 RTP 时间戳的配对 ① 算 RTT / 速率；② 音画同步的基准（见 3.4.8）
    RR（Receiver Report） 接收端 丢包率、抖动 jitter、收到的最高序号 驱动 BWE 与重传决策

    SR 里的 NTP ↔ RTP 配对是全章最关键的一处伏笔

    RTP 头里的 timestamp 不能直接跨流比较（时钟频率不同、起点随机），只有 SR 把"RTP 时间戳"锚定到"绝对墙钟 NTP"之后，音视频才有了共同的时间轴——这是 3.4.8 音画同步的地基。 另有一批带反馈语义的 RTCP 报文：NACK（要重传）、PLI / FIR（要关键帧）、REMB / TWCC（带宽估计）、SDES（CNAME，多路流归组用）。

    3.4.3 抗丢包三板斧¶

    手段 做法 代价
    NACK（重传） 接收端发现丢包 → 请求重发 增加延迟（至少 1 RTT）
    FEC（前向纠错） 多发冗余包，丢了也能算回来 多占带宽
    码率自适应（BWE） 探测带宽 → 动态降码率/分辨率/帧率 画质下降

    另有 RED（音频冗余）、RTX（重传专用流）。它们在 SDP 里也是"编码"（见 3.3.2 的 rtx/red）。

    3.4.4 横向对比：RTSP / RTMP / HLS 为什么没被本项目采用¶

    同为"流媒体方案"，对比一下才能理解为什么 WebRTC 选了 RTP/SRTP：

    RTSP + RTP RTMP HLS WebRTC（本项目）
    控制/信令 RTSP（TCP 554，文本命令） 自带 AMF 命令 HTTP 请求 自定义（本项目用 WSS）
    协商 SDP via DESCRIBE 自带握手 m3u8 索引 SDP via offer/answer
    数据面 RTP（明文，UDP） 自带 chunk 封装 HTTP 分片文件 SRTP（RTP + DTLS 加密）
    传输层 UDP（可 TCP 交织） TCP 1935 TCP 80/443 UDP（失败退化 TCP/TURN）
    穿透 NAT 无（靠端口映射） 友好（TCP） 友好 ICE / STUN / TURN
    延迟 亚秒~秒级 1~5 秒 10 秒+ 亚秒级
    抗弱网 好 差（TCP 队头阻塞） 好（可缓冲） 好（NACK/FEC/BWE）
    典型场景 安防 IPC、视频会议 直播推流（播放侧已淘汰） 大规模直播分发 实时互动、P2P 监控

    RTSP 与 RTP 是什么关系？——不是包含关系，是"控制面 + 数据面"的搭档：

    • RTSP = 遥控器（控制面）：发 OPTIONS / DESCRIBE / SETUP / PLAY / PAUSE / TEARDOWN，一个字节的视频数据都不传
    • RTP = 线缆（数据面）：真正搬运音视频包

    它们可以分开使用：WebRTC 里有 RTP 但没有 RTSP；SIP 电话是 RTP + SIP。反过来 RTSP 也几乎总是配 RTP。

    RTMP 为什么 Adobe 要自己重造一套？

    2000 年代初的替代品都不行：HTTP 渐进下载不支持直播；RTP/RTSP 走 UDP，企业防火墙大面积封堵，部署成本极高。于是 Adobe 全部自研，换来：

    优势 说明
    走 TCP 防火墙只需放行 1935（甚至 80/443），部署零成本
    Chunk Stream 分块复用 一条 TCP 连接虚拟成多条流（控制/音频/视频），音视频块交错发送，避免音频被大 I 帧堵住；块头最少 1 字节
    真正的"推流"语义 publish / play 语义清晰，天然适合上行采集 + 服务器分发
    内带元数据 AMF 传 onMetaData（分辨率/帧率/码率），客户端不用解析码流

    今天的现实地位

    推流侧 RTMP 仍是事实标准（OBS/FFmpeg/CDN 全支持）；播放侧已随 Flash 消亡，被 HLS / HTTP-FLV 取代。 本质取舍：UDP 系哲学是"过时的包不如不要"（宁可丢也要实时）；TCP 系哲学是"一个都不能少"（宁可等也要完整）。

    本项目为什么不用它们？

    1. 要亚秒级延迟（安防监控看实时画面）；
    2. 两端都是自己的 App，用 WebRTC 可P2P 直连、媒体不过服务器，省带宽成本；
    3. 自带 ICE/TURN 穿透，无需端口映射；
    4. SRTP 强制加密，安防场景必需；
    5. 需要 DataChannel 复用同一条连接传控制消息与录像文件（见 3.6）。 → 换成 RTSP/RTMP 是明显的技术倒退。

    3.4.5 本项目的通话质量为什么有时受 Wi-Fi 波动影响大¶

    结合 3.4.3 理解：Wi-Fi 丢包 → RTCP 上报 → BWE 降码率 → 画面变糊（而不是卡死）。若丢包集中且 NACK 来不及，就会出现短时马赛克/花屏（关键帧之间的 P 帧依赖断了，要等下一个 I 帧才能恢复）。

    • 缓解方向：缩短关键帧间隔、开 FEC、或让相机端在弱网下主动降分辨率（见 09 章 9.3.4）。
    • 本项目目前未开启 simulcast（signaling.dart:673-715 有一段现成的三档模板注释，启用后弱网可自动降档）。

    3.4.6 发送端：音视频是"两个打包器"，不是"两台发射机"¶

    常见误解：看到 RTPSenderVideo / RTPSenderAudio 就以为有两台并列的发射机。 准确说法：它们是 RtpSender 内部的两个打包器（packetizer）。

    pc.addTrack(videoTrack) ─► RtpTransceiver#1 ─► RtpSender(video) ─┐
                                                  └─ 内部 RTPSenderVideo
pc.addTrack(audioTrack) ─► RtpTransceiver#2 ─► RtpSender(audio) ─┐
                                                  └─ 内部 RTPSenderAudio
                                  ↓ 两个 sender 汇聚到
                    同一个 RtpTransport（BUNDLE：一条 ICE/DTLS 通道、一个 socket、一套 SRTP 密钥）
    • 轨道层：几条 track → 几个 transceiver → 几个 sender（本项目就是 2 条：audio + video）；
    • 传输层：所有 sender 共用同一条通道，靠 SSRC / mid / PayloadType 区分——这叫复用（multiplexing），不是两条物理通道。

    为什么要分成两个打包器？因为三件事完全不同：

    RTPSenderVideo RTPSenderAudio
    时间戳时钟 固定 90 kHz（与帧率无关） 采样率（Opus 48 kHz）
    一帧 ↔ 几个包 一帧常拆 N 个包（H.264 用 FU-A 分片，≤ MTU ~1200B；同一帧共用同一 timestamp，末包置 marker） 一帧一包（Opus 20 ms 约几十~几百字节）
    分包依据 RFC 6184（H.264）/ 7741（VP8）/ 7742 RFC 7587（Opus）
    丢了怎么办 接收端发 PLI / FIR 要关键帧；RTX 重传、ULPFEC NACK 重传 + RED 冗余 + in-band FEC
    省流机制 无（enabled=false 时改为发黑帧，包照发） DTX：静音期停发，只发少量 CNG

    一个反直觉的点

    视频时间戳时钟恒为 90 kHz，与帧率无关：30fps 时每帧 +3000，不是 +1。音频则用采样率（48 kHz）。 这也是为什么两条流的 timestamp 数值上完全不可比——见 3.4.8。

    一句话概括：视频"分片 + 可丢 + 靠关键帧恢复"，音频"整帧 + 冗余 + 绝不断流"。

    3.4.8 音画同步：不是"对齐 RTP timestamp"¶

    先破除误解：同步不是把两条流的 RTP timestamp 对齐。因为

    1. 视频时钟 90 kHz、音频 48 kHz，单位不同；
    2. RFC 3550 要求 timestamp 起点随机，两条流的零点毫无关系。

    所以"视频 ts=90000"与"音频 ts=48000"完全不可比。真正的同步靠三件套：

    ① RTCP SR 提供 NTP ↔ RTP 的翻译（见 3.4.2）

    发送端周期性在 SR 里同时给出「绝对墙钟 NTP」和「同一时刻的 RTP timestamp」。接收端为每个 SSRC 维护这个映射，把两条流的 RTP 时间戳都换算到同一条 NTP 时间轴上——这时才能问出"这一帧画面和这一段声音是不是同一时刻采集的"。

    ② SDP 用 a=group:LS 声明"这俩要同步"

    a=group:LS 0 1     ← Lip Sync 组：mid 0 与 mid 1 需互相同步
a=mid:0            (video)
a=mid:1            (audio)

    没有这行声明，接收端就不知道该把哪两条流对齐（多路摄像头 / 屏幕共享场景尤其关键）。

    ③ 真正执行同步的是"播放调度"，而且只调音频

    libwebrtc 由 RtpStreamsSynchronizer + StreamSynchronization 完成：

    1. 把视频当前正在播放的帧换算成 NTP → video_playout_ntp；
    2. 同样算出 audio_playout_ntp；
    3. 相减得到相对偏差 relative_delay（视频比音频快/慢多少 ms）；
    4. 把偏差作为 extra_delay_ms 交给 NetEq，让音频多缓冲 / 少缓冲去追视频——视频侧不动。

    为什么只调音频，不调视频？

    视频帧是离散的（30fps = 33 ms 一跳），调整粒度太粗，动一下就有肉眼可见的顿挫； 而音频可以用 NetEq 的 time-stretch 做亚毫秒级、听感无变化的平滑加减速。 → 音画同步的代价，是全部记在音频延迟头上的。

    还有两个防抖设计：

    • 死区：偏差在 ±~80 ms 内视作"已同步"，不动（否则会来回抖）；
    • 限速：每帧调整量有上限，防止音频加速到明显变调。

    本项目对应

    四个会破坏同步的写法

    1. 自己给视频加缓冲（为了"去抖"攒几帧再显示）= 在已算好的对齐之外又加延迟，音画必然分离；
    2. 把音视频拆成两条流分别处理、或让它们走不同的播放路径，会丢掉 LS 组关系；
    3. 长时间 enabled=false / DTX 静默：时间戳还在走但内容无效（黑帧/静音），同步基准会漂；

    状态：🟢 已填充 这一节是 3.0「分层」的收尾：本项目里有四条互相独立的媒体链路，没有一条是 RTSP/RTMP。

    产物 链路 编码 / 格式 落点
    ① 实时画面 采集 → 编码 → SRTP/RTP → 监控端 由 SDP 协商（大概率 VP8，见 P4） 不落盘，直接渲染（3.5）
    ② 事件录像 本地视频轨 → MediaRecorder → 封装 MP4（容器内是 AVCC），编码由系统编码器决定（Android 通常 H.264 + AAC） ${doc}/recordings/event_<ts>.mp4
    ③ 告警快照 FrameTap 原生取 RGB → image 包编码 PNG ${doc}/snapshots/snapshot_<ts>.png
    ④ 回放视频 MP4 文件字节流 → DataChannel → 落临时目录 → video_player 播 就是 ② 那个 MP4，原样搬运 ${tmp}/video_<id>.mp4

    关键代码：

    // rephone-security/lib/pages/camera_endpoint_page.dart:1244-1260  ② 录制
final filePath = '${saveDir.path}/event_$timestamp.mp4';
_mediaRecorder = MediaRecorder();
final tracks = _localRenderer.srcObject?.getVideoTracks();
await _mediaRecorder!.start(filePath, videoTrack: tracks.first);

// rephone-security/lib/pages/playback_page.dart:224-231  ④ 回放（DataChannel 二进制）
if (data.isBinary) {
  if (_isDownloadingVideo && _videoFileSink != null) {
    _videoFileSink!.add(data.binary);
    _receivedVideoBytes += data.binary.length;
  }
  return;
}

    ② 和 ① 是两条互不相关的编码链路

    MediaRecorder 是从本地视频轨直接录，不是把发出去的 RTP 包存下来。 所以推流用什么编码（VP8）和录下来是什么编码（通常 H.264）可以完全不同——排查"录的文件打不开/花屏"时，不要去动推流的编码设置。

    为什么回调用 DataChannel 传文件，而不是 RTMP / HTTP？¶

    考虑 结论
    媒体在哪 录像存在相机端手机上，不在服务器
    拓扑 两端已是 P2P 直连，再绕服务器上传下载是浪费
    已有通道 DataChannel（fileTransfer）已经建好且被 DTLS 加密，复用即可
    语义 回放是"取文件"，不是"看直播流"——不需要流媒体的 seek/实时语义
    成本 引入 RTMP/HTTP 要新起服务端、新开放端口、重做鉴权

    一句话：它是文件传输，不是流媒体。用 DataChannel 当"加密 U 盘"是最省事且贴合 P2P 拓扑的选择。 代价是需要自己实现分块、进度、断点（本项目已实现 video_start / video_end / video_error 三个控制消息 + 进度条）。
