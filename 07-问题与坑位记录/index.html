    07 问题与坑位记录（WebRTC 踩坑仓库）¶

    状态：🟡 骨架 + 3 条记录 ｜ 读者：正在调 WebRTC 的我自己 规则：所有 Bug/疑问一律记到这里，先现象、后结论，最终沉淀成可复用的排障手册。 每个问题贴好标签，方便以后按标签检索。

    一、怎么写一条记录（模板）¶

    ## P编号-日期-一句话标题

- **状态**：待排查 | 已修复 | 已规避 | 复现中
- **标签**：`信令` `ICE` `数据通道` `内存` `UI` `服务端` `相机端` `监控端` ...
- **现象**：看到了什么（截图/日志片段）
- **影响**：用户可感知的结果
- **排查过程**：按时间线记录做了什么实验、看了什么日志
- **根因**：一句话结论 + 涉及原理（跳转对应手册章节）
- **解决方案**：改了哪个文件哪段逻辑
- **复盘**：下次如何更快发现/避免；是否需要补进 01~06 章知识

    约定：编号连续（P1, P2, …）；日期用 YYYY-MM-DD；现象日志尽量贴原始片段并标注端别。

    P1-PC只close不dispose导致内存泄漏¶

    • 状态：已修复（代码注释固化）
    • 标签：内存 生命周期 会话清理
    • 现象：多次 相机端↔监控端 建立/断开 P2P 会话后，App 内存线性增长，最终 OOM 崩溃。
    • 影响：监控 App 长时间多次查看相机后崩溃。
    • 排查过程：定位到 _cleanSessions() / _closeSession() 只调用了 pc.close() 而没调用 pc.dispose()；flutter_webrtc 在 Web 之外是插件，native PeerConnection（网络线程/编解码器/纹理）在 close 后仍驻留。
    • 根因：flutter_webrtc 中 close() 只关会话、dispose() 才释放 native 对象。旧代码每次会话只 close 不 dispose → native 对象泄漏累积。
    • 解决方案： 
      await sess.dc?.close();
await sess.pc?.close();
await sess.pc?.dispose();   // 关键：释放 native PeerConnection
      见 signaling.dart _closeSession()/_cleanSessions()。
    • 复盘：凡是"反复建立/断开长连接"的功能，都要检查每个 native/插件对象的成对释放；相关概念见 05-状态机与生命周期.md、06-项目代码地图.md。

    P2-captureFrame取帧的三个坑（挂起/泄漏/固定文件名）¶

    • 状态：已规避（改用纹理快照，原理见 08 章 8.10）
    • 标签：截图 原生插件 挂起 内存 Android
    • 现象：监控端退出观看页时用 track.captureFrame() 存封面，偶发长时间不出图，靠 Dart 侧 .timeout(1s) 兜住才没卡死页面。
    • 影响：退出页面偶发延迟；长时间频繁截图有内存增长风险。
    • 排查过程：逐层读 flutter_webrtc-1.6.0 源码（Dart → MethodChannel → Android/iOS 原生），并检索上游 issue。
    • 根因：同一个 API 上的三个独立问题：
      1. 无超时的"等下一帧"：两端原生都是"挂一个临时接收器（addSink / addRenderer），等下一帧到来才回调"。轨道静止、对端停发或 enabled = false 时，这个 Future 永不 resolve，而 Android / iOS 两侧都没有超时（上游只在桌面端 C++ 路径补了 2s 超时）。
      2. Android 旋转分支泄漏 Bitmap：FrameCapturer.java:102-118 中，videoFrame.getRotation() != 0 时创建的 original / rotated 两张全尺寸 Bitmap 都没有 recycle()。竖屏推流的远端帧 rotation 通常就是 90/270，正好命中；横屏固定机位（rotation = 0）反而安全。
      3. 固定文件名：Dart 侧 path 硬编码 '${temp}/captureFrame.png'（media_stream_track_impl.dart:94），全 App 共用一个临时文件——并发截图互相覆盖，且从不清理。
    • 解决方案：改用 RepaintBoundary.toImage() 纹理快照（08 章 8.10），从根上不走这条链路。
    • 复盘：凡是"挂上去等回调"的插件 API，先问一句——"如果回调永远不来，我的 Future 会不会永远挂着？" 上游对应 issue：#2176/#2185（桌面端忙等 + 2s 超时，仅桌面）、#415（Android 内存泄漏，被标 wontfix 长期未修）；移动端两侧至今无超时。

    P3-toImage截外部纹理为什么macOS空白而Android正常¶

    • 状态：已确认范围（Android 实测正常，iOS 待实测）
    • 标签：截图 纹理 渲染后端 macOS
    • 现象：决定"用 RepaintBoundary.toImage() 截 RTCVideoView 当封面"是否可行时，需要先确认外部纹理在离屏光栅化下能不能拿到内容。Android 实测能正常出图。
    • 影响：直接决定封面截图方案成立与否。
    • 排查过程：读引擎源码 flow/layers/texture_layer.cc、shell/platform/embedder/embedder_external_texture_gl.cc，并对照 flutter/flutter#191797。
    • 根因：外部纹理解析是二选一——aiks_context（Impeller）或 gr_context（Skia）任一非空即可成功，两者都空则该层不产生任何绘制内容（全透明）。而 LayerTree::Flatten（离屏路径，toImage 走这条）不传 aiks_context，于是成败取决于 gr_context 是否可用：
      • macOS：Impeller 已是唯一后端，Skia 上下文为 null → 两条路都断 → 整块全透明；
      • Android：Skia 回退仍在 → 落到 ResolveTextureSkia → 正常。
    • 解决方案：Android 采用 toImage 方案；iOS 必须实测（与 macOS 同源 Metal，理论上可能命中），不能因为"代码共用"就假定可用。
    • 复盘：跨平台结论不能用"共用代码"直接外推——共用的缺失（不传 aiks_context）只是必要条件，是否真的失败还取决于该平台有没有回退路径。 另需注意 #192365：Android + Impeller-GLES 上 toImage 与 surface 销毁竞争会 use-after-free 崩溃（未修）——"能出图"不等于"不会崩"，两者是不同的问题。

    三、高频排查套路（草稿，随问题逐步打磨）¶

    3.1 "监控端显示已连接但黑屏/没声音"¶

    按层查： 1. ICE 通了吗 → 打印/看 pc.onIceConnectionState（connected 才算通）。 2. 远端有轨吗 → 相机端是否把本地轨 addTrack 进 PC（_senders 非空）；监控端 onAddRemoteStream 是否触发。 3. 渲染对了吗 → RTCVideoRenderer.srcObject 是否绑定的是远端流而非本地流。 4. 若两端不在同一网络/对称 NAT → 确认 TURN 生效（用 iceServers 里真实 uris 请求成功）。

    3.2 "相机离线/找不到了"¶

    • 看服务端日志 On Close 与 setCameraOnlineByDeviceID；
    • 确认相机端 App 是否被系统杀死（前台服务保活策略）；
    • 确认相机端 WS 是否在自动重连（每 3s）。

    3.3 "信令连不上"¶

    • host/port 与证书是否匹配（自签证书放行逻辑在 websocket.dart）；
    • 服务端 config.ini 的 cert/key 是否正确、端口是否通；
    • 看 /ws 返回码：401 场景会触发 NavigationService.handleUnauthorized()。
