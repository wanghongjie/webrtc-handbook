## 为什么需要这一章

前面 01 章已经知道媒体是 P2P 的 RTP 包。但"打包"之前，音视频原始数据经历了 采集 → 编码 → 封包；接收端反向 拆包 → 解码 → 渲染。这一章把中间的每一步讲透，理解后才能回答诸如：
- 为什么分辨率/帧率约束写在 `getUserMedia` 的 mandatory 里？

- 为什么偶发卡顿/马赛克？（丢包、无 FEC/NACK）
- 为什么相机端 CPU 发热？（**编码很贵，且很可能是软编** → 3.2.7、07 章 P4）
- 为什么回放不是"看直播"而是"下文件"？（3.6）

## 内容骨架

### 3.0 先分层：编码 ≠ 容器 ≠ 传输

> 状态：🟢 已填充
> 这一节是整章的"总纲"。搞不清这一节，后面所有概念都会串味。

学 WebRTC 时最常被这几个词绕晕：**RTMP / RTSP / RTP / H.264 / H.265**。它们经常被并列放在一起说，但**根本不在同一个层级上**：

| 名称 | 本质 | 所处层级 | 它是不是"视频流"？ |
| --- | --- | --- | --- |
| **H.264 / AVC** | 视频**压缩编码标准** | 编码层（Codec） | ❌ 它只是"怎么把像素压成字节"的算法 |
| **H.265 / HEVC** | 视频**压缩编码标准**（H.264 的下一代） | 编码层 | ❌ 同上 |
| **VP8 / VP9 / AV1** | 视频**压缩编码标准**（Google 系） | 编码层 | ❌ 同上 |
| **RTP** | 实时**传输协议**（配套 RTCP 做质量反馈） | 传输层（通常跑 UDP） | ✅ 承载层：只管"分包 + 时间戳 + 序号" |
| **RTSP** | 实时**会话控制协议**（文本协议，像 HTTP） | 控制/信令层 | ❌ 它只发 `DESCRIBE/SETUP/PLAY`，**不传数据** |
| **RTMP** | Adobe 的**一体化流媒体协议**（自带封装 + 传输） | 封装 + 传输层（TCP） | ✅ 完整方案，自成一套 |

分层之后是这样叠起来的：

```text
原始像素
   ↓  〔编码层〕H.264 / H.265 / VP8 / VP9 / AV1  —— 决定"怎么压"
压缩后的帧（裸码流）
   ↓  〔封装层〕Annex-B / AVCC / FU-A            —— 决定"怎么摆"（见 3.2.6）
   ↓  〔传输层〕RTP/SRTP（UDP） 或 RTMP（TCP）   —— 决定"怎么送"
网络包
   ↑  〔控制层〕RTSP / SDP / 自定义信令          —— 只是"遥控器"，不传数据
```

!!! tip "一句话记忆"
    **编码决定"怎么压"，封装决定"怎么摆"，传输决定"怎么送"，控制层只负责"怎么约"。**
    四者正交、可自由组合：**RTMP 里可以装 H.264；RTP 里也可以装 H.264；RTSP 控制的那条 RTP 里同样可以是 H.264 或 H.265。**
    所以"用 RTMP 还是用 H.264"是个伪问题——它们不在同一个选项集里。

!!! warning "本项目一个字都没用到 RTSP / RTMP / HLS"
    本项目（相机端 ↔ 监控端，两端都是自己的 App）**全程只走 WebRTC**：信令用 WSS、媒体用 SRTP、回放用 DataChannel 传文件。
    本章之所以仍要讲 RTSP/RTMP，是因为排查问题时最容易把这几套方案张冠李戴——见 3.4.4 的横向对比。

### 3.1 数字音视频的基本概念

> 状态：🟡 要点已填充

| 概念 | 视频 | 音频 |
| --- | --- | --- |
| 最小单位 | **帧**（一张图） | **采样点** |
| 每秒多少个 | **帧率 fps**（25/30/60） | **采样率 Hz**（48000 / 16000） |
| 单位大小 | **分辨率**（1920×1080） | **位深**（16 bit）+ **声道**（1/2） |
| 原始排列 | **像素格式**：I420 / NV12 / BGRA（见 09 章 9.4） | PCM |
| 每秒数据量 | 分辨率 × 帧率 × 1.5 字节 | 采样率 × 位深/8 × 声道 |

**码率（bitrate）= 数据量 / 时间**，是"画质 ↔ 带宽"的权衡旋钮。一段 1080p30 的未压缩 YUV：

```text
1920 × 1080 × 1.5 字节 × 30 帧 ≈ 93 MB/s ≈ 750 Mbps
```

而压缩后（H.264）通常只要 **2~5 Mbps**——差了两个数量级，这就是编码存在的意义。

> **本项目的采集约束对应关系**：`signaling.dart:607-626` 的 `mediaConstraints` 里写 `minWidth/minHeight/minFrameRate`，这是对**采集**的期望（注意是"期望"不是"承诺"，实际会被设备能力与带宽自适应改写——详见 09 章 9.7）。
> 它**约束的是分辨率/帧率，与用什么编码无关**。

### 3.2 编解码器（Codec）

> 状态：🟢 已填充

#### 3.2.1 为什么必须压缩（1 秒 1080p 未压缩 ≈ 上百 MB）

见 3.1 的算式。**不压缩就没法在网络上实时传**，这是硬约束。

#### 3.2.2 H.264 / AVC 与 H.265 / HEVC

**命名要先说清：一个标准、两个名字**——视频编码标准由 ITU-T 和 ISO/IEC 联合发布，所以同一份标准有两套编号：

| 通俗叫法 | ITU-T 编号 | ISO/IEC 编号 | 正式英文名（缩写） |
| --- | --- | --- | --- |
| **H.264** | H.264 | MPEG-4 Part 10 | **AVC** = Advanced Video Coding |
| **H.265** | H.265 | MPEG-H Part 2 | **HEVC** = High Efficiency Video Coding |

所以 **H.264 == AVC，H.265 == HEVC**，就是"土豆"和"马铃薯"。代码里见到 `video/avc`、`avc1`、`hvc1`，指的就是它们。

| 维度 | H.264 / AVC（2003） | H.265 / HEVC（2013） |
| --- | --- | --- |
| 压缩率 | 基准 | **同画质省约 40~50% 码率** |
| 基本单元 | 宏块**固定 16×16** | CTU 最大 **64×64**，四叉树自适应切分 |
| 帧内预测方向 | 9 种 | **35 种** |
| 编码复杂度 | 基线 | **编码端 2~10 倍**，解码端 1.5~2 倍 |
| 专利授权 | MPEG LA 一家，清晰 | **三家专利池**（MPEG LA / HEVC Advance / Velos），混乱 |
| 生态支持 | 几乎所有芯片/浏览器**全部支持** | 硬件与浏览器支持残缺 |
| **WebRTC** | ✅ 支持 | ❌ **不支持**（libwebrtc 无 HEVC） |

!!! warning "H.265 没进实时通信领域的根因"
    H.265 是"用 2~10 倍编码算力 + 一堆专利麻烦，换 40% 带宽"。
    移动端长时间推流时，**编码算力直接转换成发热和耗电**——本项目相机端正是"一部手机开着摄像头连续推流数小时"，这笔账是亏的。

#### 3.2.3 VP8 / VP9 / AV1（Google 系，免专利）

这是**另一条 lineage**，和 ITU/ISO 的 H.26x 系列是竞争关系：

| 编码 | 出身 | 对标 | 关键卖点 |
| --- | --- | --- | --- |
| **VP8** | On2 开发，Google 2010 收购后开源 | H.264 | **免版税（royalty-free）** |
| **VP9** | Google 自研 | H.265 | 效率接近 HEVC，但**编码复杂度远低于 HEVC** |
| **AV1** | AOMedia 联盟（Google/Netflix/Amazon/Apple…） | 超越 H.265 | 免专利 + 比 VP9 再省 30%，但**算力极高** |

- VP8/VP9 通常装在 **WebM** 容器里，配 **Opus/Vorbis** 音频——这是 Google 的一整套免专利组合拳。
- **VP8 是 WebRTC 的强制项**：RFC 7742 规定 WebRTC 实现**必须支持 VP8 和 H.264**（音频必须支持 Opus 和 G.711）。这就是"任何两个 WebRTC 端点一定能通话"的兜底。
- **VP8/VP9 没有 NALU 概念**（见 3.2.5），它们是"帧 + 自带 frame header"的结构，参数写在帧头里，不需要额外传参数集。

#### 3.2.4 压缩到底怎么做的：四类冗余

编码器干的事，就是**找出并扔掉四类冗余**：

| 冗余类型 | 大白话 | 做法 |
| --- | --- | --- |
| **时间冗余**（贡献最大） | 相邻两帧几乎一样，只有一小块在动 | **运动估计/运动补偿**：在上一帧"找"这块内容跑哪去了，只记**运动矢量**（"这块往右挪 30px"）+ 一小块**残差** |
| **空间冗余** | 一整片蓝天，不用逐像素记 | **帧内预测**：用周围已编好的像素"猜"当前块，只编码猜不准的差值 |
| **视觉冗余**（有损的根源） | 人眼对亮度敏感、对颜色不敏感；对轮廓敏感、对细微纹理不敏感 | ① **4:2:0 色度抽样**（颜色信息砍到 1/4）<br>② **DCT 变换 + 量化**：转频域后把高频系数按 QP 成批抹零 |
| **编码冗余**（无损） | 数据里还有统计规律（比如一串 0） | **熵编码**（CAVLC / CABAC），类似 ZIP |

**量化步长 QP** 就是平时说的"画质/码率旋钮"：QP 越大 → 抹掉越多 → 码率越低、画面越糊（块效应、振铃）。

**三种帧类型**（由时间冗余引出）：

| 帧 | 参考谁 | 特点 |
| --- | --- | --- |
| **I 帧**（关键帧 / IDR） | 自包含，不参考别人 | 体积最大；是**随机访问点**（拖动进度条）和**错误恢复点** |
| **P 帧** | 只参考**前面**的帧 | 靠运动矢量 + 残差 |
| **B 帧** | **前后双向**参考 | 压缩率最高，但要等"未来帧"到达 → **引入缓冲延迟** |

!!! note "为什么实时通话基本不用 B 帧"
    B 帧要求"后面的帧先到"，天然带来乱序和缓冲。追求亚秒级延迟的 WebRTC/直播场景**通常禁用 B 帧**——这也是"实时流"和"离线压制"画质/延迟取舍的分水岭。
    **本项目没有干预这项**，由 libwebrtc 按实时场景默认处理。

一串从一个 I 帧到下一个 I 帧之间的帧叫一个 **GOP（Group of Pictures）**。本项目录 10 秒一段 MP4，GOP 长度直接影响起播与拖动体验。

#### 3.2.5 编码器的产物：裸码流与 NALU

**裸码流（Elementary Stream, ES）** = 只有编码压缩后的视频数据本身，**没有**外面那层包装：

| 层级 | 例子 | 能否直接播放 |
| --- | --- | --- |
| **裸码流 ES** | `.h264` / `.hevc` 文件 | ❌ 能解码，但**没有时间戳、没有音轨、没有元数据**，没法"播放" |
| + 时间戳 = PES | TS 流里的一路 | 部分 |
| + 容器封装 | `.mp4` / `.mov` / `.ts` | ✅ 完整可播放 |

H.264 把裸码流组织成一串 **NALU（Network Abstraction Layer Unit）**，每个 NALU 有类型：

| NALU 类型 | 内容 | 属于 |
| --- | --- | --- |
| **SPS** | 全局参数：分辨率、profile、level | non-VCL |
| **PPS** | 图像参数：熵编码方式、QP 等 | non-VCL |
| **IDR / I 帧片** | 关键帧数据 | VCL（真像素） |
| **非 IDR 片** | P/B 帧数据 | VCL |
| **SEI / AUD** | 附加信息 / 分隔符 | non-VCL |

!!! warning "SPS/PPS 必须先给到解码器"
    否则解码器就算拿到帧数据也不知道怎么解（不知道分辨率和参数）。**"SPS/PPS 放哪儿"正是下面三种摆放方式的核心差异。**

#### 3.2.6 裸码流的三种摆放方式：Annex-B / AVCC / RTP

NALU 长度**任意**（SPS 可能 30 字节，1080p 的 I 帧可能 500 KB）。三种格式本质上都在解决"这一串 NALU 怎么被正确读出来"，但**约束条件不同**：

| | **Annex-B** | **AVCC** | **RTP（RFC 6184）** |
| --- | --- | --- | --- |
| 本质 | 字节流的**定界格式** | 文件的**定界格式** | **网络传输协议** |
| 解决什么问题 | 连续字节流里找边界 | 文件中精确定位 | MTU 适配 + 时序 + 丢包/乱序 |
| 分隔方式 | 起始码 `00 00 00 01` | **长度前缀**（通常 4 字节） | **不需要**（UDP 包天然有边界） |
| SPS/PPS | **内联**在流里，关键帧前重复发 | 抽到 **`avcC` box**（带外） | SDP 的 `sprop-parameter-sets` 或 STAP-A |
| 大 NALU 怎么办 | 不管（整块写） | 不管（整块写） | **FU-A 主动分片** |
| 时间戳/丢包检测 | ❌ | ❌ | ✅ |
| 随机访问 | 差（要扫字节） | **好**（可算偏移） | 不适用 |
| 中途接入 | **好**（随时拿到参数） | 差（必须先读头） | 好 |
| 典型场景 | TS、直播、`.h264` | **MP4 / MOV / MKV** | WebRTC、RTSP+UDP |

```text
Annex-B : ... 00 00 00 01 [SPS] 00 00 00 01 [PPS] 00 00 00 01 [I帧 500KB] ...
AVCC    : [00 00 00 1E][SPS 30B]  [00 00 07 A1 20][I帧 500KB] ...
                长度=30                长度=500000
RTP     : 500KB 的 I 帧 → 拆成几百个 FU-A 包，每包带「开始/中间/结束」标志
```

!!! tip "Annex-B ↔ AVCC 可以无损互转"
    只是换分隔符、搬 SPS/PPS 位置，NALU 内容一个字节都不变。FFmpeg 的 `h264_mp4toannexb` / `h264_annexbtoavcc` 就是干这个的。

!!! note "最精妙的对比点"
    **起始码/长度前缀的存在，是因为"没有天然边界"；而 UDP 包本身就是天然边界。**
    所以 RTP **不需要**任何一种定界符，它需要的反而是**相反的能力**——把一个太大的 NALU **拆开**（FU-A）。
    RFC 6184 定义了：`Single NALU`（小包直通）、**`FU-A`**（大 NALU 分片，最常用）、`STAP-A`（多个小 NALU 聚合，常用来一起发 SPS+PPS）。

> **本项目链路对照**：编码器输出 → libwebrtc 内部 → **RTP（FU-A/STAP-A）** 发给监控端；同时本地录制分支另走 **MP4（AVCC）** 落盘——详见 3.6。

#### 3.2.7 软编 vs 硬编

| | 软件编码（libvpx / OpenH264） | 硬件编码（MediaCodec / VideoToolbox） |
| --- | --- | --- |
| 跑在哪 | CPU | 专用 DSP/GPU 模块 |
| 功耗发热 | **高** | **低** |
| 兼容性 | 什么格式都能编 | 取决于芯片（**H.264 基本全覆盖，VP8/VP9 编码支持很参差**） |
| 画质/码率控制 | 通常更精细 | 相对粗糙、档位少 |

本项目相机端是**手机长时间前台推流**，这一项直接决定用户体验：

!!! warning "一个值得实测的怀疑（见 07 章 P4）"
    本项目**没有指定编码**，走 libwebrtc 默认优先级（VP8 在 H.264 之前），而 **VP8 在移动端通常是软件编码**（硬件编码器一般只做 H.264/HEVC）。
    若属实，相机端会有**不必要的发热与耗电**。验证与改法见 3.3.6 与 07 章 P4。

### 3.3 SDP：编码能力是"怎么约定"的

> 状态：🟢 已填充（真实 SDP 样例仍是 TODO）
> 这一节回答一个关键问题：**发送方和接收方是怎么知道对方用什么编码、用什么摆放方式的？**

#### 3.3.1 SDP 长什么样

SDP（Session Description Protocol，RFC 4566）就是一段**纯文本**的"自我介绍书"，不是传输协议。行格式固定为 `x=value`：

| 行 | 含义 |
| --- | --- |
| `v=` / `o=` / `s=` / `t=` | 版本 / 会话发起者 / 会话名 / 时间 |
| `c=` | 连接信息 |
| **`m=`** | **媒体行**：`m=<媒体类型> <端口> <传输协议> <payload type 列表>` |
| `a=rtpmap` | payload type ↔ 编码格式 的**映射声明** |
| `a=fmtp` | 该编码的**附加参数** |
| `a=sendrecv` / `sendonly` / `recvonly` | 媒体方向 |
| `a=mid` | Unified-Plan 下一条 m-line 的标识 |
| `a=ice-ufrag` / `a=fingerprint` … | ICE 与 DTLS 参数（见 04 章） |

**Unified-Plan**：一条 `m-line` = 一个 transceiver（收发器）。本项目 `sdpSemantics: 'unified-plan'`（`signaling.dart:115`），现代标准，旧的 `plan-b` 已废弃。

> **本项目方向**：相机端发画面（`sendonly`），监控端收画面；监控端开启对讲时会**重协商**加入麦克风轨（见 `setMonitorTalkbackEnabled()`，`signaling.dart:253-295`）。
> ⚠️ 注意 offer 里 `OfferToReceiveAudio/Video: true` 声明的是"**我想收**"，不是"我能发"。

#### 3.3.2 核心机制：payload type 映射表

这是"怎么约定"的真正答案。**RTP 包头里只有 7 bit 的 Payload Type 字段（0~127）**，双方要做的就是约定好"几号 = 什么编码"这张表：

- **0~95 静态编号**（IANA 固定分配，如 0 = PCMU 音频）——视频基本没分到静态号
- **96~127 动态编号**——**必须**由 SDP 临时声明含义

一段真实的 video m-line：

```sdp
m=video 9 UDP/TLS/RTP/SAVPF 96 97 98 99 100 101 102
                             ↑ 顺序 = 优先级，越靠前越想要
a=rtpmap:96 VP8/90000
a=rtpmap:97 rtx/90000
a=rtpmap:98 H264/90000
a=fmtp:98 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f
a=rtpmap:100 VP9/90000
a=rtpmap:102 red/90000
```

| 行 | 含义 |
| --- | --- |
| `96 97 98 …` | 本端**支持的所有** payload type，**按偏好排序** |
| `a=rtpmap:96 VP8/90000` | 96 号 = VP8，时钟 **90000 Hz**（视频固定 90 kHz） |
| `a=rtpmap:98 H264/90000` | 98 号 = H.264 |
| `rtx` / `red` / `ulpfec` | 重传 / 冗余 / 前向纠错的辅助"编码"（可靠性产物，不是原始数据） |

> **协商只做一次（握手时传 SDP），此后每个 RTP 包只用 7 bit 说自己是几号**，接收方查表交给对应解码器——这就是为什么实时传输不需要每包带冗长的格式描述。

#### 3.3.3 offer/answer 协商规则（RFC 3264；WebRTC 走 JSEP RFC 8829）

```text
① 发起方 offer  : 列出自己支持的所有 codec，按偏好排序
② 应答方 answer : 只能从 offer 的列表里挑自己支持的
                  ✗ 不能引入 offer 里没有的 codec
                  ✓ 可以裁剪掉自己不支持的
                  ✓ 可以重排顺序，表达自己的偏好
③ 最终生效      : 取 answer 里排在最前面的那个
```

**真正的双向对话**，且 answer 可以"降级"——这正是跨设备兼容性的来源。

#### 3.3.4 `fmtp` 里唯一被协商的"打包细节"

Annex-B vs AVCC **从不协商**（由容器规范写死，见 3.2.6）。但 RTP 有一个**真正需要协商**的打包参数：

```sdp
a=fmtp:98 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f
```

| 参数 | 含义 |
| --- | --- |
| **`packetization-mode`** | **0** = 只允许 Single NALU（大帧发不出去，基本不可用）<br>**1** = 允许 **FU-A 分片 + STAP-A 聚合**（实际必选） |
| **`profile-level-id`** | H.264 的 profile/level（如 `42e01f` = Baseline Level 3.1）。**两端必须匹配**，否则可能协商失败或解码异常 |
| `level-asymmetry-allowed=1` | 允许收发使用不同 level（如发 720p、收 480p） |
| `sprop-parameter-sets` | base64 的 SPS/PPS，**带外**提前告知（也可改用 STAP-A 带内发送，中途重连更可靠） |

#### 3.3.5 设备怎么知道"我支持什么"？（三层叠加）

这是个高频疑问。答案是**三层共同决定，WebRTC 只规定最底下那层**：

| 层 | 谁决定 | 决定什么 |
| --- | --- | --- |
| **① 标准下限** | **RFC 7742**（视频）/ RFC 7874（音频） | WebRTC 实现**必须**支持 **VP8 + H.264 Constrained Baseline**；音频必须支持 **Opus + G.711**。这是**互通性兜底**，不禁止支持更多 |
| **② 编译全集** | **libwebrtc 的 GN 编译开关**（`rtc_use_h264` / `rtc_libvpx_build_vp9` / `rtc_enable_av1`）+ 预编译产物版本 | 编解码器是**编进 .so / .framework** 的，版本锁死则全集固定 |
| **③ 运行时子集** | **查询平台硬件** | Android 用 `MediaCodecList` 按 MIME 枚举（`MIMETYPE_VIDEO_AVC/HEVC/VP8/VP9/AV1`）；iOS 用 VideoToolbox（H.264 全系硬编，HEVC 需 A10+）。硬件不支持则回落软编或不可用 |

!!! warning "推论：同一份 Flutter 代码，在不同手机上生成的 SDP 可能不一样"
    第 ③ 层是设备相关的。所以**不能靠推理断定"本项目一定在用什么编码"，必须运行时实测**。

> ⚠️ **H.264 的历史包袱**：开源 libwebrtc **默认不自带 H.264**（专利 + 需链接 OpenH264/FFmpeg），必须显式开 `rtc_use_h264=true`。
> 本项目用的是 flutter-webrtc 维护的**预编译产物**（Android `io.github.webrtc-sdk:android:150.7871.01`，`android/app/build.gradle:122`；iOS 同版本 CocoaPods），一般已启用——但**这点必须实测确认**，不能想当然。

### 3.4 RTP / RTCP：媒体怎么在网络上跑

> 状态：🟢 已填充

#### 3.4.1 RTP 头：7 bit 说清"我是什么编码"

RTP（RFC 3550）跑在 UDP 上，**每个包只负责搬运，不管重传、不管顺序**：

```text
┌─ RTP 头 ────────────────────────────────┬─ RTP 载荷 ─────────┐
│ PT=98 │ seq │ timestamp │ SSRC │ marker │  编码后的 NALU 数据 │
└─────────────────────────────────────────┴────────────────────┘
```

| 字段 | 作用 |
| --- | --- |
| **Payload Type（7 bit）** | 编码格式代号 → 查 SDP 建的表 |
| **Sequence Number** | **重排序**（UDP 会乱序）+ 检测丢包 |
| **Timestamp** | 采样时刻 → 接收端用 **jitter buffer** 按正确节奏播放，消除网络抖动 |
| **SSRC** | 同步源标识 → 区分多路流 |
| **Marker bit** | 视频里常用来标"这是一帧的最后一个包" |

同一帧的多个 FU-A 包**共用同一个 timestamp**（90 kHz），接收端据此拼回一帧。

#### 3.4.2 RTCP：质量反馈（RTP 的孪生兄弟，必须配套）

RTCP 周期性互发**收发报告**：丢了多少包、抖动多大、往返时延多少。发送端据此做**拥塞控制**与**码率自适应**——网络差了就降码率。

> 这就是 WebRTC 能做到"不卡"的核心机制。本项目完全交给 libwebrtc，代码不感知。

RTCP 不止"汇报丢包"，两类报文分工不同：

| 报文 | 谁发 | 内容 | 用途 |
| --- | --- | --- | --- |
| **SR**（Sender Report） | 发送端 | 发包数/字节数 **+ NTP 时间戳与对应 RTP 时间戳的配对** | ① 算 RTT / 速率；② **音画同步的基准**（见 3.4.8） |
| **RR**（Receiver Report） | 接收端 | 丢包率、抖动 jitter、收到的最高序号 | 驱动 BWE 与重传决策 |

!!! important "SR 里的 NTP ↔ RTP 配对是全章最关键的一处伏笔"
    RTP 头里的 timestamp **不能直接跨流比较**（时钟频率不同、起点随机），只有 SR 把"RTP 时间戳"锚定到"绝对墙钟 NTP"之后，音视频才有了**共同的时间轴**——这是 3.4.8 音画同步的地基。
    另有一批带反馈语义的 RTCP 报文：**NACK**（要重传）、**PLI / FIR**（要关键帧）、**REMB / TWCC**（带宽估计）、**SDES**（CNAME，多路流归组用）。

#### 3.4.3 抗丢包三板斧

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| **NACK**（重传） | 接收端发现丢包 → 请求重发 | 增加延迟（至少 1 RTT） |
| **FEC**（前向纠错） | 多发冗余包，丢了也能算回来 | 多占带宽 |
| **码率自适应（BWE）** | 探测带宽 → 动态降码率/分辨率/帧率 | 画质下降 |

另有 **RED**（音频冗余）、**RTX**（重传专用流）。它们在 SDP 里也是"编码"（见 3.3.2 的 `rtx`/`red`）。

#### 3.4.4 横向对比：RTSP / RTMP / HLS 为什么没被本项目采用

同为"流媒体方案"，对比一下才能理解为什么 WebRTC 选了 RTP/SRTP：

| | **RTSP + RTP** | **RTMP** | **HLS** | **WebRTC（本项目）** |
| --- | --- | --- | --- | --- |
| 控制/信令 | RTSP（TCP 554，文本命令） | 自带 AMF 命令 | HTTP 请求 | **自定义（本项目用 WSS）** |
| 协商 | SDP via `DESCRIBE` | 自带握手 | m3u8 索引 | **SDP via offer/answer** |
| 数据面 | RTP（明文，UDP） | 自带 chunk 封装 | HTTP 分片文件 | **SRTP（RTP + DTLS 加密）** |
| 传输层 | UDP（可 TCP 交织） | **TCP 1935** | TCP 80/443 | UDP（失败退化 TCP/TURN） |
| 穿透 NAT | 无（靠端口映射） | 友好（TCP） | 友好 | **ICE / STUN / TURN** |
| 延迟 | 亚秒~秒级 | 1~5 秒 | **10 秒+** | **亚秒级** |
| 抗弱网 | 好 | 差（TCP 队头阻塞） | 好（可缓冲） | **好（NACK/FEC/BWE）** |
| 典型场景 | **安防 IPC、视频会议** | 直播**推流**（播放侧已淘汰） | 大规模直播分发 | 实时互动、P2P 监控 |

**RTSP 与 RTP 是什么关系？**——**不是包含关系，是"控制面 + 数据面"的搭档**：

- **RTSP = 遥控器**（控制面）：发 `OPTIONS / DESCRIBE / SETUP / PLAY / PAUSE / TEARDOWN`，**一个字节的视频数据都不传**
- **RTP = 线缆**（数据面）：真正搬运音视频包

它们**可以分开使用**：WebRTC 里有 RTP 但没有 RTSP；SIP 电话是 RTP + SIP。反过来 RTSP 也几乎总是配 RTP。

**RTMP 为什么 Adobe 要自己重造一套？**

2000 年代初的替代品都不行：HTTP 渐进下载不支持直播；RTP/RTSP 走 **UDP**，企业防火墙大面积封堵，部署成本极高。于是 Adobe 全部自研，换来：

| 优势 | 说明 |
| --- | --- |
| **走 TCP** | 防火墙只需放行 1935（甚至 80/443），部署零成本 |
| **Chunk Stream 分块复用** | 一条 TCP 连接虚拟成多条流（控制/音频/视频），**音视频块交错发送**，避免音频被大 I 帧堵住；块头最少 **1 字节** |
| **真正的"推流"语义** | `publish` / `play` 语义清晰，天然适合上行采集 + 服务器分发 |
| **内带元数据** | AMF 传 `onMetaData`（分辨率/帧率/码率），客户端不用解析码流 |

!!! note "今天的现实地位"
    **推流侧 RTMP 仍是事实标准**（OBS/FFmpeg/CDN 全支持）；**播放侧已随 Flash 消亡**，被 HLS / HTTP-FLV 取代。
    **本质取舍**：UDP 系哲学是"过时的包不如不要"（宁可丢也要实时）；TCP 系哲学是"一个都不能少"（宁可等也要完整）。

**本项目为什么不用它们？**

1. **要亚秒级延迟**（安防监控看实时画面）；
2. **两端都是自己的 App**，用 WebRTC 可**P2P 直连、媒体不过服务器**，省带宽成本；
3. 自带 **ICE/TURN 穿透**，无需端口映射；
4. **SRTP 强制加密**，安防场景必需；
5. 需要 **DataChannel** 复用同一条连接传控制消息与录像文件（见 3.6）。
   → 换成 RTSP/RTMP 是**明显的技术倒退**。

#### 3.4.5 本项目的通话质量为什么有时受 Wi-Fi 波动影响大

结合 3.4.3 理解：Wi-Fi 丢包 → RTCP 上报 → BWE 降码率 → 画面变糊（而不是卡死）。若丢包集中且 NACK 来不及，就会出现**短时马赛克/花屏**（关键帧之间的 P 帧依赖断了，要等下一个 I 帧才能恢复）。

- 缓解方向：缩短关键帧间隔、开 FEC、或让相机端在弱网下主动降分辨率（见 09 章 9.3.4）。
- 本项目目前**未开启 simulcast**（`signaling.dart:673-715` 有一段现成的三档模板注释，启用后弱网可自动降档）。

#### 3.4.6 发送端：音视频是"两个打包器"，不是"两台发射机"

> 常见误解：看到 `RTPSenderVideo` / `RTPSenderAudio` 就以为有两台并列的发射机。
> 准确说法：**它们是 `RtpSender` 内部的两个打包器（packetizer）**。

```text
pc.addTrack(videoTrack) ─► RtpTransceiver#1 ─► RtpSender(video) ─┐
                                                  └─ 内部 RTPSenderVideo
pc.addTrack(audioTrack) ─► RtpTransceiver#2 ─► RtpSender(audio) ─┐
                                                  └─ 内部 RTPSenderAudio
                                  ↓ 两个 sender 汇聚到
                    同一个 RtpTransport（BUNDLE：一条 ICE/DTLS 通道、一个 socket、一套 SRTP 密钥）
```

- **轨道层**：几条 track → 几个 transceiver → 几个 sender（本项目就是 2 条：audio + video）；
- **传输层**：所有 sender **共用同一条通道**，靠 **SSRC / mid / PayloadType** 区分——这叫**复用（multiplexing）**，不是两条物理通道。

为什么要分成两个打包器？因为三件事完全不同：

| | `RTPSenderVideo` | `RTPSenderAudio` |
| --- | --- | --- |
| 时间戳时钟 | **固定 90 kHz**（与帧率无关） | **采样率**（Opus 48 kHz） |
| 一帧 ↔ 几个包 | 一帧常拆 N 个包（H.264 用 **FU-A** 分片，≤ MTU ~1200B；同一帧共用同一 timestamp，末包置 marker） | **一帧一包**（Opus 20 ms 约几十~几百字节） |
| 分包依据 | RFC 6184（H.264）/ 7741（VP8）/ 7742 | RFC 7587（Opus） |
| 丢了怎么办 | 接收端发 **PLI / FIR** 要关键帧；RTX 重传、ULPFEC | **NACK 重传 + RED 冗余 + in-band FEC** |
| 省流机制 | 无（`enabled=false` 时改为发黑帧，包照发） | **DTX**：静音期停发，只发少量 CNG |

!!! note "一个反直觉的点"
    视频时间戳时钟**恒为 90 kHz，与帧率无关**：30fps 时每帧 `+3000`，不是 `+1`。音频则用采样率（48 kHz）。
    这也是为什么两条流的 timestamp **数值上完全不可比**——见 3.4.8。

一句话概括：**视频"分片 + 可丢 + 靠关键帧恢复"，音频"整帧 + 冗余 + 绝不断流"**。

#### 3.4.7 接收端：解复用之后，两条路走完全不同的容错哲学

```text
UDP socket
   ↓ SRTP 解密
RtpDemuxer（按 SSRC / mid / PayloadType 解复用）          ← 音视频在这一层才被分开
   ↓                                    ↓
RTPReceiverVideo                    RTPReceiverAudio
   ↓                                    ↓
按 seq + timestamp 组帧                NetEq
   ↓                                    ↓
FrameBuffer（等帧 / 排序 / 判过期）     抖动自适应 + PLC + 变速(time-stretch) + 解码
   ↓                                    ↓
VideoDecoder（硬解）                   PCM → ADM（AudioTrack / AudioUnit）播放
   ↓
VideoFrame → VideoSink 广播 → Flutter textureId（3.5）
```

| | 视频 | 音频 |
| --- | --- | --- |
| 缓冲器 | `FrameBuffer` | **`NetEq`**（WebRTC 音频最核心的算法） |
| 抖动变大 | 多等一会儿 → 延迟上升（画面顿一下但连续） | 自动加大缓冲 → 延迟上升（宁可延迟，不能破音） |
| 丢包 | 等下一个 I 帧（短时花屏 / 马赛克） | **PLC** 合成一段（轻微失真，不断流） |
| 缓冲空了 / 积压 | **丢帧**保流畅 | **变速播放**（轻微加减速，不变调） |
| 能不能丢 | **能**（帧可丢） | **不能**（一帧都不能丢） |

!!! tip "`NetEq` 是什么"
    它一个模块干四件事：**抖动缓冲 + 丢包补偿(PLC) + 解码 + 变速不变调(time-stretch)**。
    "音频为什么听起来永远连续、而视频会卡一下"——答案就在这里：音频用**时间换连续**，视频用**丢帧换实时**。

#### 3.4.8 音画同步：不是"对齐 RTP timestamp"

**先破除误解**：同步**不是**把两条流的 RTP timestamp 对齐。因为

1. 视频时钟 90 kHz、音频 48 kHz，**单位不同**；
2. RFC 3550 要求 timestamp **起点随机**，两条流的零点毫无关系。

所以"视频 ts=90000"与"音频 ts=48000"**完全不可比**。真正的同步靠三件套：

**① RTCP SR 提供 NTP ↔ RTP 的翻译（见 3.4.2）**

发送端周期性在 SR 里同时给出「绝对墙钟 NTP」和「同一时刻的 RTP timestamp」。接收端为每个 SSRC 维护这个映射，把两条流的 RTP 时间戳**都换算到同一条 NTP 时间轴**上——这时才能问出"这一帧画面和这一段声音是不是同一时刻采集的"。

**② SDP 用 `a=group:LS` 声明"这俩要同步"**

```text
a=group:LS 0 1     ← Lip Sync 组：mid 0 与 mid 1 需互相同步
a=mid:0            (video)
a=mid:1            (audio)
```

没有这行声明，接收端就不知道该把哪两条流对齐（多路摄像头 / 屏幕共享场景尤其关键）。

**③ 真正执行同步的是"播放调度"，而且只调音频**

libwebrtc 由 `RtpStreamsSynchronizer` + `StreamSynchronization` 完成：

1. 把视频当前正在播放的帧换算成 NTP → `video_playout_ntp`；
2. 同样算出 `audio_playout_ntp`；
3. 相减得到**相对偏差** `relative_delay`（视频比音频快/慢多少 ms）；
4. **把偏差作为 `extra_delay_ms` 交给 NetEq，让音频多缓冲 / 少缓冲去追视频**——**视频侧不动**。

!!! question "为什么只调音频，不调视频？"
    视频帧是离散的（30fps = 33 ms 一跳），调整粒度太粗，动一下就有肉眼可见的顿挫；
    而音频可以用 NetEq 的 time-stretch 做**亚毫秒级、听感无变化**的平滑加减速。
    → **音画同步的代价，是全部记在音频延迟头上的。**

还有两个防抖设计：

- **死区**：偏差在 ±~80 ms 内视作"已同步"，不动（否则会来回抖）；
- **限速**：每帧调整量有上限，防止音频加速到明显变调。

**本项目对应**

```dart
// signaling.dart:656-664
pc.onTrack = (event) {
  if (event.streams.isEmpty) return;
  final stream = event.streams[0];
  if (event.track.kind == 'video')      onAddRemoteStream?.call(newSession, stream);
  else if (event.track.kind == 'audio') onAddRemoteAudioStream?.call(newSession, stream);
};
```

`event.streams[0]` 说明远端的 audio 与 video **属于同一个 `MediaStream`**（即 SDP 里那个 `LS` 组）。**只要当同一条流消费，libwebrtc 自动完成同步，业务代码什么都不用做。**

!!! warning "四个会破坏同步的写法"
    1. **自己给视频加缓冲**（为了"去抖"攒几帧再显示）= 在已算好的对齐之外又加延迟，音画必然分离；
    2. **把音视频拆成两条流分别处理**、或让它们走不同的播放路径，会丢掉 `LS` 组关系；
    3. **长时间 `enabled=false` / DTX 静默**：时间戳还在走但内容无效（黑帧/静音），同步基准会漂；
    4. **视频渲染器与音频播放设备本就不同源**（屏幕刷新 vs 声卡时钟），任何额外的中间处理都会放大漂移。

**排查顺序**：先分清是网络问题还是渲染问题 —— 看 `getStats()` 里 inbound-rtp 的：

- 音频侧 `jitterBufferDelay` 异常高 → NetEq 一直在扛抖动，**延迟就是这样被吃掉的**；
- 视频侧 `packetsLost` 高 → 在等 I 帧（表现为花屏而非音画不同步）；
- 两者都正常却仍不同步 → 回头查上面 1、2 两条。

#### 3.5.4 `addSink`：唯一的绑定落点


- `addSink` 是 libwebrtc 的标准观察者接口。**从这一行起，解码线程每产出一帧就回调 `SurfaceTextureRenderer.onFrame()`**。

#### 3.5.5 一帧的生命周期：Android 与 iOS 走了两条完全不同的路

| | Android | iOS |
| --- | --- | --- |
| 帧入口 | `SurfaceTextureRenderer.onFrame(VideoFrame)` | `FlutterRTCVideoRenderer.renderFrame:` |
| 传递方式 | **GPU 共享**：EGL 直接画到纹理背后的 Surface | **CPU 拷贝**：I420 → `CVPixelBuffer` |
| 旋转 | libwebrtc / GPU 完成 | 手写 `RTCYUVHelper I420Rotate` |
| 通知引擎 | 提交 EGLSurface（引擎自行合成） | `[_registry textureFrameAvailable:_textureId]` |
| 引擎取数 | 无需回调 | 引擎主动调 `copyPixelBuffer` |
| 开销 | 低（无拷贝） | 每帧一次 memcpy + 旋转 |

Android：**Surface 在第一帧到达时才创建**，`producer.setSize()` 用帧的旋转后分辨率：

```java
// $PUB/android/.../SurfaceTextureRenderer.java:100
public void onFrame(VideoFrame frame) {
  synchronized (surfaceLock) {
    if (surface == null) {
      producer.setSize(frame.getRotatedWidth(), frame.getRotatedHeight());
      surface = producer.getSurface();
      createEglSurface(surface);
    } else if (frameSizeChanged(frame)) {
      // The producer's backing buffers are fixed-size: setSize() only takes
      // effect for a Surface obtained afterwards. Without recreating the EGL
      // surface here, a simulcast layer upgrade keeps rendering into the old
      // low-resolution buffer and the video stays blurry.
      releaseEglSurface(() -> {});
      surface = null;                                   // 先置空，避免 getSurface 抛异常后画进已释放的 Surface
      producer.setSize(frame.getRotatedWidth(), frame.getRotatedHeight());
      surface = producer.getSurface();
      createEglSurface(surface);
    }
  }
  updateFrameDimensionsAndReportEvents(frame);
  super.onFrame(frame);   // EglRenderer：投递到自己的渲染线程，用 GlRectDrawer 把帧画到 EGLSurface
}
```

> **坑位**：`SurfaceProducer` 的底层 buffer 是**定长**的，`setSize()` 只对「之后获取的 Surface」生效。所以在 `else if` 分支里**必须 release EGLSurface → setSize → 重新 getSurface → createEglSurface**。否则 simulcast 从低清层升到高清层时，画面会一直停留在旧的低分辨率上（模糊），而分辨率事件却已经上报给 Dart 了（表现为「布局变对了，画面还是糊的」）。

| 点 | 说明 |
| --- | --- |
| 为什么要赋两次 `srcObject` | unified-plan 下 audio/video 的 `onTrack` 顺序不定；有视频轨时才绑主渲染器，音频轨后到再赋一次以刷新部分机型的播放（`monitor_viewer_page.dart:102-103` 注释） |

!!! warning "② 和 ① 是两条互不相关的编码链路"
    `MediaRecorder` 是**从本地视频轨直接录**，不是把发出去的 RTP 包存下来。
    所以**推流用什么编码（VP8）和录下来是什么编码（通常 H.264）可以完全不同**——排查"录的文件打不开/花屏"时，不要去动推流的编码设置。

#### 为什么回调用 DataChannel 传文件，而不是 RTMP / HTTP？

| 考虑 | 结论 |
| --- | --- |
| 媒体在哪 | 录像**存在相机端手机上**，不在服务器 |
| 拓扑 | 两端已是 P2P 直连，再绕服务器上传下载是浪费 |
| 已有通道 | DataChannel（`fileTransfer`）**已经建好且被 DTLS 加密**，复用即可 |
| 语义 | 回放是"**取文件**"，不是"**看直播流**"——不需要流媒体的 seek/实时语义 |
| 成本 | 引入 RTMP/HTTP 要新起服务端、新开放端口、重做鉴权 |

> 一句话：**它是文件传输，不是流媒体**。用 DataChannel 当"加密 U 盘"是最省事且贴合 P2P 拓扑的选择。
> 代价是需要自己实现分块、进度、断点（本项目已实现 `video_start` / `video_end` / `video_error` 三个控制消息 + 进度条）。
