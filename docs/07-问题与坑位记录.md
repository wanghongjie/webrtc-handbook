## P1-PC只close不dispose导致内存泄漏

- **状态**：已修复（代码注释固化）
- **标签**：`内存` `生命周期` `会话清理`
- **现象**：多次 相机端↔监控端 建立/断开 P2P 会话后，App 内存线性增长，最终 OOM 崩溃。
- **影响**：监控 App 长时间多次查看相机后崩溃。
- **排查过程**：定位到 `_cleanSessions()` / `_closeSession()` 只调用了 `pc.close()` 而没调用 `pc.dispose()`；flutter_webrtc 在 Web 之外是插件，native `PeerConnection`（网络线程/编解码器/纹理）在 close 后仍驻留。
- **根因**：flutter_webrtc 中 `close()` 只关会话、`dispose()` 才释放 native 对象。旧代码每次会话只 close 不 dispose → native 对象泄漏累积。
- **解决方案**：
  ```dart
  await sess.dc?.close();
  await sess.pc?.close();
  await sess.pc?.dispose();   // 关键：释放 native PeerConnection
  ```
  见 `signaling.dart` `_closeSession()`/`_cleanSessions()`。
- **复盘**：凡是"反复建立/断开长连接"的功能，都要检查**每个 native/插件对象的成对释放**；相关概念见 `05-状态机与生命周期.md`、`06-项目代码地图.md`。

## P2-captureFrame取帧的三个坑（挂起/泄漏/固定文件名）

- **状态**：已规避（改用纹理快照，原理见 [08 章 8.10](08-媒体流与渲染链路.md)）
- **标签**：`截图` `原生插件` `挂起` `内存` `Android`
- **现象**：监控端退出观看页时用 `track.captureFrame()` 存封面，偶发长时间不出图，靠 Dart 侧 `.timeout(1s)` 兜住才没卡死页面。
- **影响**：退出页面偶发延迟；长时间频繁截图有内存增长风险。
- **排查过程**：逐层读 `flutter_webrtc-1.6.0` 源码（Dart → MethodChannel → Android/iOS 原生），并检索上游 issue。
- **根因**：同一个 API 上的三个独立问题：
    1. **无超时的"等下一帧"**：两端原生都是"挂一个临时接收器（`addSink` / `addRenderer`），等下一帧到来才回调"。轨道静止、对端停发或 `enabled = false` 时，这个 Future **永不 resolve**，而 Android / iOS **两侧都没有超时**（上游只在桌面端 C++ 路径补了 2s 超时）。
    2. **Android 旋转分支泄漏 Bitmap**：`FrameCapturer.java:102-118` 中，`videoFrame.getRotation() != 0` 时创建的 `original` / `rotated` 两张全尺寸 Bitmap **都没有 `recycle()`**。竖屏推流的远端帧 rotation 通常就是 90/270，**正好命中**；横屏固定机位（rotation = 0）反而安全。
    3. **固定文件名**：Dart 侧 path 硬编码 `'${temp}/captureFrame.png'`（`media_stream_track_impl.dart:94`），全 App 共用一个临时文件——并发截图互相覆盖，且从不清理。
- **解决方案**：改用 `RepaintBoundary.toImage()` 纹理快照（[08 章 8.10](08-媒体流与渲染链路.md)），从根上不走这条链路。
- **复盘**：凡是"挂上去等回调"的插件 API，先问一句——**"如果回调永远不来，我的 Future 会不会永远挂着？"**
  上游对应 issue：[#2176](https://github.com/flutter-webrtc/flutter-webrtc/issues/2176)/[#2185](https://github.com/flutter-webrtc/flutter-webrtc/pull/2185)（桌面端忙等 + 2s 超时，**仅桌面**）、[#415](https://github.com/flutter-webrtc/flutter-webrtc/issues/415)（Android 内存泄漏，被标 `wontfix` 长期未修）；移动端两侧至今无超时。

## P3-toImage截外部纹理为什么macOS空白而Android正常

- **状态**：已确认范围（Android 实测正常，iOS 待实测）
- **标签**：`截图` `纹理` `渲染后端` `macOS`
- **现象**：决定"用 `RepaintBoundary.toImage()` 截 `RTCVideoView` 当封面"是否可行时，需要先确认外部纹理在**离屏光栅化**下能不能拿到内容。Android 实测**能正常出图**。
- **影响**：直接决定封面截图方案成立与否。
- **排查过程**：读引擎源码 `flow/layers/texture_layer.cc`、`shell/platform/embedder/embedder_external_texture_gl.cc`，并对照 [flutter/flutter#191797](https://github.com/flutter/flutter/issues/191797)。
- **根因**：外部纹理解析是**二选一**——`aiks_context`（Impeller）或 `gr_context`（Skia）**任一非空**即可成功，两者都空则该层不产生任何绘制内容（全透明）。而 `LayerTree::Flatten`（离屏路径，`toImage` 走这条）**不传 `aiks_context`**，于是成败取决于 `gr_context` 是否可用：
    - **macOS**：Impeller 已是唯一后端，Skia 上下文为 `null` → 两条路都断 → 整块全透明；
    - **Android**：Skia 回退仍在 → 落到 `ResolveTextureSkia` → 正常。
- **解决方案**：Android 采用 `toImage` 方案；**iOS 必须实测**（与 macOS 同源 Metal，理论上可能命中），不能因为"代码共用"就假定可用。
- **复盘**：跨平台结论**不能用"共用代码"直接外推**——共用的缺失（不传 `aiks_context`）只是必要条件，是否真的失败还取决于**该平台有没有回退路径**。
  另需注意 [#192365](https://github.com/flutter/flutter/issues/192365)：Android + Impeller-GLES 上 `toImage` 与 surface 销毁竞争会 use-after-free 崩溃（**未修**）——"能出图"不等于"不会崩"，两者是不同的问题。

## P4-相机端实际编码疑似VP8软编

- **状态**：**待排查**（目前是基于源码阅读的推测，**尚未真机实测**）
- **标签**：`编码` `发热` `功耗` `相机端` `SDP`
- **现象**：（尚未观测）预期表现为相机端长时间前台推流时**明显发热、掉电快**。
- **影响**：相机端被当作"常开摄像头"使用，编码功耗直接决定可用时长与是否触发系统降频/杀进程。
- **排查过程**：
    1. 读 `signaling.dart:641-644` —— `createPeerConnection` **只传了 `iceServers` 与 `sdpSemantics`，没有任何 codec 参数**；
    2. 读 `signaling.dart:841-846` —— `_fixSdp()` 是**空壳**，注释掉的那行正是 codec 相关改写，说明作者原本预留了这个钩子但没启用；
    3. 结论：**编码完全交给 libwebrtc 默认优先级**（VP8 在 H.264 之前）；
    4. 而 **VP8 在 Android/iOS 上通常是软件编码**（硬件编码器一般只做 H.264/HEVC）→ 推断相机端在跑软编。
- **根因（推测）**：未指定 codec + libwebrtc 默认 VP8 优先 + 移动端 VP8 多无硬件编码 = **用 CPU 做了一件本可以交给芯片的事**。
- **待验证动作**（按顺序，零风险优先）：
    1. 在 `_fixSdp` 里打印 `m=video` 与所有 `a=rtpmap` / `a=fmtp` 行，用 `pull_logs.sh` 在**相机端与监控端各抓一次**，确认实际协商结果（做法见 `03` 章 3.3.6）；
    2. 同时调 `getRtpSenderCapabilities('video')` / `getRtpReceiverCapabilities('video')`，确认两端 send/recv 能力是否对称；
    3. 若确认是 VP8，则在**两端**同时锁定 H.264（`_fixSdp` 过滤 或 `setCodecPreferences`），再对比发热与画质。
- **解决方案**：（待实测后填写）
- **复盘**：
    - 凡是"**设备长时间做重算力任务**"的场景（长时推流、长时录制），**第一件事就是确认走没走硬件**；
    - 编码选择**不能靠推理**——它同时受"SDK 编译产物"与"设备硬件"两层影响，同一份代码在不同手机上结果可能不同（`03` 章 3.3.5）；
    - 本项目两端是同一 App + 同一 SDK 版本，所以"编码全集"一致，**两端同时改 H.264 是安全的**（RFC 7742 保证 H.264 必被支持）。
- **相关知识**：`03` 章 3.2.7（软硬编）、3.3.5（设备能力三层）、3.3.6（观测与改法）。

## P5-同进程二次打开同一颗相机被抢与restartVideo释放顺序

- **状态**：已规避（插件侧，flutter_webrtc 1.6.2+hotfix.4）+ 已修复（本项目侧，注释已固化）
- **标签**：`相机` `采集` `生命周期` `内存` `相机端`
- **现象**：反复切换前后摄像头 / 重建视频流时，logcat 出现 `CameraAccessException(CAMERA_ERROR=3)`，底层是 HAL 的 `cancelRequest` 返回 `ENOSYS(-38, Function not implemented)`；另一路表现是反复重建后 native 相机/纹理句柄泄漏、内存线性上涨。
- **影响**：切换摄像头失败或预览黑屏；长时间运行后 OOM。
- **排查过程**：读 `GetUserMediaImpl.java:751-781` 的注释与 `buildSharedVideoTrack()`，再对照本项目 `signaling.dart:560-605` 的 `restartVideo()`。
- **根因**：两件独立的事
    1. **相机被抢**：同一进程对同一颗 camera device 开第二个 `CameraCaptureSession` 时，cameraserver 会把它从第一个 client 手里"偷走"，第一个 session 收到 `onDisconnected()` → 内部 `close() → stopRepeating() → cancelRequest()`，此时 HAL 正在拆管线，返回 `ENOSYS`；而 Android 的 `CameraCaptureSessionImpl.onDisconnected` **不处理这个错误**，直接冒泡成 `CameraAccessException(CAMERA_ERROR=3)`。这是 **AOSP Camera2 框架自身的缺陷**（Pixel 原生机也复现），不是某个厂商的锅。
    2. **释放顺序**：重建流时如果先 `dispose` 旧流再切渲染器，渲染器会引用已释放的流；如果只 stop video track 而不 stop audio track、不 dispose stream，则 audio track 与 native 句柄泄漏。
- **解决方案**：
    - **插件侧（已具备）**：`getUserMedia` 时若发现同朝向/同 `deviceId` 的相机已活跃，**不再开第二个 session**，而是复用已有 `VideoSource` 派生一条新 `VideoTrack`（`buildSharedVideoTrack()`，主/从 track 通过 `primaryTrackId` 记账，只有主 track 被移除时才真正 `stopCapture/dispose`）。
    - **本项目侧**：`restartVideo()` 严格按四步走（顺序不可换）：
      ```text
      ① stop 所有 track（video + audio），等 500ms 让硬件释放
      ② createStream() 建新流（触发 onLocalStream，UI 与 renderer 切到新流）
      ③ sender.replaceTrack(newVideoTrack)  ← 利用 unified-plan 的 sender 换轨，无需重协商
      ④ 最后才 oldStream.dispose()          ← 必须在 renderer 已切走之后
      ```
- **复盘**：
    - "同一硬件资源被开两次"这类问题**先怀疑框架/系统层**，再怀疑自己代码——注释里明确写了"stock AOSP (Pixel) 也复现"。
    - 凡是"重建采集资源"的流程，**顺序即正确性**：先停后建、先切后放（见 `05` 章生命周期、`09` 章 9.9 的 `detach` 约束）。
    - 换轨优先用 `replaceTrack`，比"重新协商 SDP"轻得多，但前提是**必须走 unified-plan 才能拿到 `RTCRtpSender`**（`09` 章 9.10.1）。

## 三、高频排查套路（草稿，随问题逐步打磨）

### 3.1 "监控端显示已连接但黑屏/没声音"
按层查：
1. ICE 通了吗 → 打印/看 `pc.onIceConnectionState`（`connected` 才算通）。
2. 远端有轨吗 → 相机端是否把本地轨 addTrack 进 PC（`_senders` 非空）；监控端 `onAddRemoteStream` 是否触发。
3. 渲染对了吗 → `RTCVideoRenderer.srcObject` 是否绑定的是远端流而非本地流。
4. 若两端不在同一网络/对称 NAT → 确认 TURN 生效（用 `iceServers` 里真实 uris 请求成功）。

### 3.2 "相机离线/找不到了"
- 看服务端日志 `On Close` 与 `setCameraOnlineByDeviceID`；
- 确认相机端 App 是否被系统杀死（前台服务保活策略）；
- 确认相机端 WS 是否在自动重连（每 3s）。

### 3.3 "信令连不上"
- host/port 与证书是否匹配（自签证书放行逻辑在 `websocket.dart`）；
- 服务端 `config.ini` 的 cert/key 是否正确、端口是否通；
- 看 `/ws` 返回码：401 场景会触发 `NavigationService.handleUnauthorized()`。

### 3.4 "相机端发热 / 画面糊 / 延迟高"
先分清是**编码**问题还是**网络**问题（见 `03` 章 3.2、3.4）：
1. **确认实际编码** → 打 SDP 的 `m=video` 行或调 `getRtpSenderCapabilities('video')`。若跑的是 VP8，移动端多为软编 → 发热（P4）。
2. **确认是降码率还是丢包** → 画面持续糊但流畅 = BWE 主动降码率（带宽不足）；马赛克/花屏 = 丢包后等下一个 I 帧。
3. **确认采集参数** → `createStream()` 的约束只是"期望"，实际会被设备能力与自适应改写（09 章 9.7），别假设固定尺寸。
4. **弱网兜底** → 考虑启用 `signaling.dart:673-715` 现成的 simulcast 三档模板。
